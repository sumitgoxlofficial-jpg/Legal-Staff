# Partner Network — audit, architecture and policies

## 1. Audit of the existing LegalStaff (done before any change)

| Area | Finding |
| --- | --- |

About 600 SEO pages are generated by `node seo/build.mjs` from `seo/pages/*.mjs` with one shared header/footer in `seo/lib.mjs`. `admin.html` is a hand-written vanilla-JS console. |

| Directory | `directory.html`, table `directory_applications` (status pending/info/verified/rejected), review by platform admins, public read only of verified rows through `directory_profiles()`. Anonymous applications are inserted straight into the table. |
| **Payments for the directory** | **None.** The directory is free: no price, no checkout. Existing payments (`payments`, `functions/upi-pay`) are for practice-software subscriptions. The proposed ₹49 lifetime listing therefore does not exist today. |
| Documents | The directory records only file **names and sizes** (the page says files are not uploaded yet). |
| Notifications | Resend email (`notify`, `auth-email`, `admin`). WhatsApp wired but not connected. No SMS. |

### Consequences for this build
* The listing price is stored as **unset / unreconciled**. A super admin must set it, compare it with the public pricing and mark it approved (System Settings). The Partner Network never displays or charges it.
* A commission needs a **verified payment record**. With no directory payment flow, staff record a verified payment (Advocate Registrations → Record payment), or a future payment webhook can call the same SQL with the service role. Nothing is read from a browser payment response.
* "Required documents submitted" can only mean "document names recorded", until the directory uploads real files.

## 2. Architecture

* **All rules live in PostgreSQL** (`supabase/migrations/0024_partner_network.sql`). Every table is locked (RLS on, no grants to `anon`/`authenticated`). The browser calls `SECURITY DEFINER` functions: `partner_*` (a signed-in partner, only their own rows), `admin_*` (staff, permission re-checked on every call) and three public functions. Hiding a button is never the control.
* Reused, not duplicated: Supabase Auth users, `super_admins`, `directory_applications`, Resend, the existing design (`static/site.css`, generated header/footer via `seo/lib.mjs`), existing admin shell.
* New: tables (`partners`, `partner_categories`, `partner_applications`, `partner_documents`, `partner_referrals`, `referral_attributions`, `partner_commissions`, `partner_payouts`, `partner_payment_methods`, `partner_campaigns`, `partner_resources`, `partner_notifications`, `partner_terms_acceptance`, `partner_compliance_approvals`, `partner_audit_logs`, `partner_fraud_flags`, `partner_settings`, plus `partner_roles`, `partner_staff`, `partner_templates`, `partner_support_tickets`, `partner_listing_payments`, `partner_rate_limits`).
* Pages (`seo/pages/partners.mjs`): `/partners`, `/partners/register|login|terms|privacy`, portal shells `/partners/dashboard|referrals|earnings|payouts|profile|resources|support` (noindex, excluded from the sitemap). Logic in `static/partners.js`; styling `static/partners.css` (site tokens only).
* Admin: new **Partner Network** tab in the existing console with an 18-item left menu (`static/admin-partners.js`).
* Email: `functions/partner-mail` drains queued notifications and sends template test emails; `0025` schedules it.
* Directory hook: `directory.html` captures `?ref=`, records the click server-side and sends `referral_code` + `visitor_token` with the application. Triggers on `directory_applications` do the rest and **cannot break registration** (errors are caught and logged to `partner_audit_logs`).

## 3. Policies (implemented as written)

**Attribution.** First valid referral wins. A click is recorded by the server (`partner_track_click`, rate-limited, deduplicated per 30 minutes). At application time the code and the visitor token are checked: partner active, category tracking on, not a self-referral (same email, same mobile in any format, same enrolment number), click inside the window (30 days, setting). The attribution row is immutable (trigger) and the claim on the advocate row cannot be rewritten. Staff may *confirm* (when no click matched) or *override* with a reason, both audited.
* **Existing advocate accounts**: attribution happens only when the directory application is created; an advocate who already applied (or any later `?ref=`) is never attributed. Enrolment numbers are unique, so there is no second application.
* **Conflicting links**: the first valid link within 30 days is kept; later links are ignored and never tracked.
* **Direct registrations**: no attribution row, no commission.
* **Repeat visits**: deduplicated; they do not extend the window.
* Without a matching click the application is still attributed but flagged (`no_matching_click`, score 25) and its commission waits in **Pending Attribution** for staff confirmation. Browser storage alone is never trusted.

**Commission.** Off for every category (a CHECK constraint makes "on without a legal approval reference" impossible). Switching a category on requires an unexpired recorded counsel approval for that category; the approval must be on record **before** the referral was attributed; revoking the last valid approval switches the category off. A ledger entry exists only when the global switch, category switch and approval are all open. Status engine: pending attribution → pending payment → pending verification → eligible (valid attribution, verified payment, documents recorded, listing verified, risk below hold threshold) → approved → payable → paid; plus on hold, rejected, reversed. One commission per attribution (unique key). Rejecting a listing after the fact reverses unpaid commissions and flags paid ones for clawback.

**Fraud.** Scored flags (self-referral 100, repeated payment reference 80, burst of registrations 30, unmatched click 25, clawback 60), manual flags, manual review, reversal. IP/device similarity is not collected or used as proof.

**Payouts.** UPI/bank details encrypted with `pgcrypto` using a key in Vault; only a masked value is ever returned to partners; staff reveal is audited. A payout needs verified KYC, a method, the minimum balance, and takes all payable commissions atomically; one open payout per partner; UTR mandatory and unique.

**Roles.** Super Admin (existing `super_admins`), Admin, Finance Manager, Partner Manager, Marketing Manager, Support Manager, Partner, plus custom roles (Super Admin only). 20 permissions, enforced in SQL.

## 4. Legal review required before any commission is activated
Counsel must review: BCI Rule 36 and restrictions on advocates sharing remuneration or paying for referrals; directory content and all marketing material; each category's compensation arrangement; the DPDP Act 2023 and Rules (notice, consent, retention, correction/erasure); the draft Partner Terms and Partner Privacy Notice (both marked as drafts). The Compliance screen records the approval reference, scope, approver and validity.
